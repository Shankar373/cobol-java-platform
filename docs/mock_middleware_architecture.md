# Mock Middleware Architecture

> This document defines the design for mock DB2/CICS/IMS/MQ services used in the COBOL to Java modernization pipeline.
> These mocks enable deterministic differential testing when real mainframe middleware is unavailable.

---

## 1. Design Principles

1. **Deterministic**: Given the same fixture config, the mock produces identical outputs every run.
2. **Config-driven**: Fixture data (SQL rows, CICS map responses, IMS segments, MQ messages) defined in YAML/JSON alongside the COBOL repo.
3. **Bidirectional**: Both the legacy side (GnuCOBOL-compatible wrapper or mock-COBOL runner) and the Java side use the same fixture data.
4. **Minimally invasive**: Mocks are generated as Java helper classes injected at startup; no changes to generated COBOL business logic.
5. **Replaceable**: In production, swap mock classes for real Spring Data JPA / Spring Integration / IBM MQ JMS implementations via Spring profiles.

## 2. Mock SQL Service (DB2 / EXEC SQL)

### 2.1 Architecture

```
COBOL EXEC SQL statement
    |
    v
native_generator.py generates:
    SpringContextHelper.jdbcTemplate.query(...) / .update(...)
    |
    v
MockSqlService.java (generated helper)
    |
    v
H2 in-memory DataSource (pre-seeded from mock_db.yaml)
```

### 2.2 Fixture Config Format (mock_db.yaml)

Location: `tests/repos/<REPO>/mock_db.yaml`

```yaml
tables:
  - name: CUSTOMER
    columns:
      - name: CUST_ID
        type: INTEGER
        primary_key: true
      - name: CUST_NAME
        type: VARCHAR(20)
      - name: DEPT_ID
        type: INTEGER
    rows:
      - [101, "TEST CUSTOMER       ", 10]
      - [102, "ANOTHER CUST        ", 10]
      - [103, "DEPT B CUST         ", 20]
  - name: ORDERS
    columns:
      - name: ORDER_ID
        type: INTEGER
        primary_key: true
      - name: CUST_ID
        type: INTEGER
      - name: ORDER_DATE
        type: DATE
    rows:
      - [1001, 101, "2024-01-15"]
```

### 2.3 MockSqlService.java (Generated)

Generated by `modernize/native_pipeline.py` when `has_sql=True` and `mock_db.yaml` exists.

```java
package com.systema.modernized;

public class MockSqlService {
    private static org.springframework.jdbc.datasource.embedded.EmbeddedDatabase db;
    private static org.springframework.jdbc.core.JdbcTemplate jdbcTemplate;

    public static void initialize() {
        if (db != null) return;
        db = new org.springframework.jdbc.datasource.embedded.EmbeddedDatabaseBuilder()
            .setType(org.springframework.jdbc.datasource.embedded.EmbeddedDatabaseType.H2)
            .addScript("classpath:mock_schema.sql")
            .addScript("classpath:mock_data.sql")
            .build();
        jdbcTemplate = new org.springframework.jdbc.core.JdbcTemplate(db);
        SpringContextHelper.jdbcTemplate = jdbcTemplate;
    }

    public static void shutdown() {
        if (db != null) db.shutdown();
    }
}
```

The generated schema/data SQL scripts are written from the mock_db.yaml content by `native_pipeline.py`.

### 2.4 Integration Points

- GnuCOBOL side (mock-COBOL baseline): A Python-generated mock runner pre-seeds an H2 instance using the same mock_db.yaml and executes the COBOL logic through a Java bridge layer that intercepts EXEC SQL calls.
- Java transpiled side: MockSqlService.initialize() called in the generated program's main() before execute().
- Differential comparison: both sides write SQLCODE, SQLSTATE, and selected column values to stdout; Gate 1 compares stdout.

### 2.5 Supported SQL Operations

| Operation | Mock Behavior |
|---|---|
| SELECT INTO | Query H2; bind result columns to host variables |
| INSERT | Execute H2 insert; set SQLCODE=0 on success |
| UPDATE | Execute H2 update; set SQLCODE=0 on success |
| DELETE | Execute H2 delete; set SQLCODE=0 on success |
| DECLARE/OPEN/FETCH/CLOSE CURSOR | SqlRowSet on H2; FETCH advances cursor |
| COMMIT | H2 transaction commit |
| ROLLBACK | H2 transaction rollback |
| NOT FOUND | H2 EmptyResultDataAccessException -> SQLCODE=100 |
| CONSTRAINT VIOLATION | H2 DataIntegrityViolationException -> SQLCODE=-803 |

## 3. Mock CICS Service (EXEC CICS)

### 3.1 Architecture

```
COBOL EXEC CICS command
    |
    v
native_generator.py generates:
    CicsTransactionContext.sendMap(...) / .receiveMap(...)
    |
    v
CicsTransactionContext.java (generated helper)
    |
    v
mock_cics.yaml (fixture: scripted map responses)
```

### 3.2 Fixture Config Format (mock_cics.yaml)

Location: `tests/repos/<REPO>/mock_cics.yaml`

```yaml
transaction_id: "ORDR"
maps:
  - name: ORDMAP1
    fields:
      - name: CUST-ID-IN
        position: 1
        length: 9
        type: NUMERIC
      - name: ORDER-AMT-IN
        position: 10
        length: 9
        type: DECIMAL
        scale: 2
scripted_responses:
  - trigger: SEND_MAP ORDMAP1
    receive_fields:
      CUST-ID-IN: "000000101"
      ORDER-AMT-IN: "000010050"
eib_values:
  EIBTRNID: "ORDR"
  EIBCALEN: 0
```

### 3.3 CicsTransactionContext.java (Generated)

```java
package com.systema.modernized;

public class CicsTransactionContext {
    private static java.util.Map<String, java.util.Map<String, String>> scriptedResponses = new java.util.HashMap<>();
    private static java.util.Map<String, String> eibValues = new java.util.HashMap<>();

    public static void initialize(String configJson) {
        // Parse JSON config; populate scriptedResponses and eibValues
    }

    public static void sendMap(String mapName, byte[] mapData) {
        // Log map send for differential comparison
        System.out.println("CICS SEND MAP: " + mapName);
    }

    public static java.util.Map<String, String> receiveMap(String mapName) {
        return scriptedResponses.getOrDefault("SEND_MAP " + mapName, new java.util.HashMap<>());
    }

    public static String getEib(String fieldName) {
        return eibValues.getOrDefault(fieldName, "");
    }

    public static int getResp() { return 0; }
    public static int getResp2() { return 0; }
}
```

### 3.4 BMS Map Parsing (Phase C.4a)

The BMS parser (modernize/bms_parser.py) is extended to:
1. Parse DFHMDF macros: extract field names, positions (LINE/COL), lengths (LENGTH), and attributes (ATTRB).
2. Generate a JSON/YAML representation of the map layout.
3. Feed this into the mock_cics.yaml structure for field binding.

### 3.5 CICS to REST Mapping (Phase E)

For production refactoring, EXEC CICS SEND MAP generates:
- A Spring MVC `@PostMapping` endpoint that accepts a JSON payload with the same field names.
- A Spring MVC `@GetMapping` endpoint that returns the map data as JSON.

## 4. Mock IMS Service (EXEC DLI)

### 4.1 Architecture

```
COBOL CALL 'CBLTDLI' USING func-code, pcb-ptr, io-area, ssa
    |
    v
native_generator.py generates:
    ImsMockService.call(funcCode, pcbName, ioArea, ssa)
    |
    v
ImsMockService.java (generated helper)
    |
    v
mock_ims.yaml (fixture: segment tree data)
```

### 4.2 Fixture Config Format (mock_ims.yaml)

Location: `tests/repos/<REPO>/mock_ims.yaml`

```yaml
databases:
  - name: CUSTDB
    pcb: CUSTPCB
    root_segment: CUSTOMER
    segments:
      - name: CUSTOMER
        key_field: CUST-ID
        key_length: 9
        segment_length: 50
        children:
          - name: ORDER
            key_field: ORDER-ID
            key_length: 9
            segment_length: 30
    data:
      - CUSTOMER:
          CUST-ID: "000000101"
          CUST-NAME: "TEST CUSTOMER       "
          children:
            - ORDER:
                ORDER-ID: "000001001"
                ORDER-AMT: "000010050"
```

### 4.3 ImsMockService.java (Generated)

Implements DL/I function codes against an in-memory tree structure:

| DL/I Code | Java Implementation |
|---|---|
| GU (Get Unique) | Find segment by SSA key qualifier |
| GN (Get Next) | Advance cursor to next segment at current level |
| GNP (Get Next in Parent) | Advance within current parent's children |
| GHU/GHN/GHNP (Get Hold) | Same as G variants; marks segment as held for update |
| ISRT (Insert) | Add new segment to tree |
| DLET (Delete) | Remove held segment from tree |
| REPL (Replace) | Update held segment data |

## 5. Mock MQ Service (IBM MQ)

### 5.1 Architecture

```
COBOL CALL 'MQPUT' / 'MQGET'
    |
    v
native_generator.py generates:
    MqMockService.mqPut(queueName, messageDescriptor, messageBuffer)
    MqMockService.mqGet(queueName, messageDescriptor, messageBuffer)
    |
    v
MqMockService.java (backed by in-memory java.util.Deque)
```

### 5.2 Fixture Config Format (mock_mq.yaml)

Location: `tests/repos/<REPO>/mock_mq.yaml`

```yaml
queues:
  - name: INPUT.QUEUE
    pre_seeded_messages:
      - message_id: "MSG001"
        correlation_id: "COR001"
        payload: "ORDER|101|2024-01-15|100.50"
  - name: OUTPUT.QUEUE
    pre_seeded_messages: []
```

### 5.3 MqMockService.java (Generated)

```java
package com.systema.modernized;

public class MqMockService {
    private static java.util.Map<String, java.util.Deque<byte[]>> queues = new java.util.HashMap<>();

    public static void initialize(String configJson) {
        // Parse configJson; pre-seed queues from mock_mq.yaml
    }

    public static int mqPut(String queueName, Object msgDesc, byte[] buffer) {
        queues.computeIfAbsent(queueName, k -> new java.util.ArrayDeque<>()).addLast(buffer.clone());
        return 0; // MQCC_OK
    }

    public static int mqGet(String queueName, Object msgDesc, byte[] buffer) {
        java.util.Deque<byte[]> q = queues.get(queueName);
        if (q == null || q.isEmpty()) return 2033; // MQRC_NO_MSG_AVAILABLE
        byte[] msg = q.pollFirst();
        System.arraycopy(msg, 0, buffer, 0, Math.min(msg.length, buffer.length));
        return 0; // MQCC_OK
    }
}
```

### 5.4 MQ Copybook Stubs (CMQV.cpy, CMQODV.cpy)

Generate stub copybooks with minimum constants required for GnuCOBOL compilation:

```cobol
       * CMQV.cpy - IBM MQ Constants Stub
        01 MQCC-OK             PIC S9(9) COMP VALUE 0.
        01 MQCC-WARNING        PIC S9(9) COMP VALUE 1.
        01 MQCC-FAILED         PIC S9(9) COMP VALUE 2.
        01 MQRC-NONE           PIC S9(9) COMP VALUE 0.
        01 MQRC-NO-MSG-AVAILABLE PIC S9(9) COMP VALUE 2033.
        01 MQOO-INPUT-AS-Q-DEF PIC S9(9) COMP VALUE 1.
        01 MQOO-OUTPUT         PIC S9(9) COMP VALUE 16.
```

These stubs enable GnuCOBOL compilation so the legacy baseline can be captured (minus MQ calls, which are replaced with mock calls).

## 6. Integration with Pipeline

### 6.1 Config Discovery

The pipeline discovers mock config files at Stage 1 (Discover):
- `mock_db.yaml` -> sets `has_mock_sql = True` in discover state
- `mock_cics.yaml` -> sets `has_mock_cics = True`
- `mock_ims.yaml` -> sets `has_mock_ims = True`
- `mock_mq.yaml` -> sets `has_mock_mq = True`

### 6.2 Generate Stage (Stage 6)

When mock configs are present, native_pipeline.py generates additional helper classes:
- `MockSqlService.java` (if has_mock_sql)
- `CicsTransactionContext.java` (if has_mock_cics)
- `ImsMockService.java` (if has_mock_ims)
- `MqMockService.java` (if has_mock_mq)
- SQL seed scripts: `mock_schema.sql`, `mock_data.sql`

### 6.3 Baseline Alternative (Mock-COBOL Runner)

For middleware-blocked programs, the Baseline stage uses a mock-COBOL runner instead of GnuCOBOL:
1. A Python script (`modernize/mock_cobol_runner.py`) reads mock config files.
2. Intercepts EXEC SQL calls, queries H2 using the same mock_db.yaml.
3. Intercepts EXEC CICS calls, returns scripted responses from mock_cics.yaml.
4. Writes the same stdout/files a real GnuCOBOL execution would produce.
5. This mock-COBOL output becomes the Gate 1 baseline.

The Java transpiled code then runs against the same mock services; Gate 1 compares the two outputs.

### 6.4 Configuration Example (migration_config.json extension)

```json
{
  "middleware": {
    "sql": { "mock_config": "mock_db.yaml" },
    "cics": { "mock_config": "mock_cics.yaml" },
    "ims": { "mock_config": "mock_ims.yaml" },
    "mq": { "mock_config": "mock_mq.yaml" }
  },
  "baseline": {
    "mode": "mock",
    "mock_runner": "modernize/mock_cobol_runner.py"
  }
}
```

## 7. Production Replacement Path

When migrating to production with real middleware:

| Mock Service | Production Replacement |
|---|---|
| MockSqlService (H2) | Spring Data JPA with real DB2 JDBC driver; enable `-Pdb2` Maven profile |
| CicsTransactionContext | Spring MVC REST controllers; map JSON payloads to BMS field equivalents |
| ImsMockService | Spring Data with JPA/JDBC mapping to IMS DB2 equivalents; or IMS Universal JDBC Driver |
| MqMockService | Spring Integration with IBM MQ JMS provider; replace Deque with MQQueueManager |

All replacements are injected via Spring profiles; the business logic in generated COBOL Java classes requires no change.
